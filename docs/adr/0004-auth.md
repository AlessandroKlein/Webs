# ADR-0004: JWT + refresh token opaco + RBAC

- **Estado:** Aceptado
- **Fecha:** 2026 (versión 0.1.0 del monorepo)
- **Decisión:** Autenticación con **JWT de acceso** (15 min) + **refresh token opaco**
  (30 días, rotación), y autorización **RBAC** con permisos `<recurso>.<accion>`.

## Contexto

El panel de administración y el sitio público necesitan autenticación y control de acceso
fino. El access token debe permitir autorizar sin consultar la BD en cada petición; el
refresh token debe ser revocable y seguro frente a robo.

## Decisión

- **Access token**: JWT firmado con `JWT_SECRET`, TTL de 15 minutos
  (`ACCESS_TOKEN_TTL_SECONDS = 60 * 15`), payload `{ sub, email, permissions }`. Se envía en
  `Authorization: Bearer` y en el frontend se guarda solo en memoria.
- **Refresh token**: valor **opaco** (`randomBytes(48).toString('hex')`), TTL de 30 días
  (`REFRESH_TOKEN_TTL_MS`), almacenado en BD **hasheado** (SHA-256) en `Session.refreshToken`.
  Se entrega por **cookie `httpOnly`** (`webs_refresh_token`, `sameSite: lax`, `secure` en
  producción) **y también en el body** de login/register/refresh.
- **Rotación**: cada `refresh` revoca la sesión actual (`revokedAt`) y emite una nueva.
- **RBAC**: roles (`Role`) ↔ permisos (`Permission`) en muchos-a-muchos; usuarios ↔ roles en
  muchos-a-muchos. Roles de sistema `super_admin`, `admin`, `editor`, `user` sembrados en
  `apps/api/prisma/seed.ts`.
- **Permisos**: convención `<recurso>.<accion>` (p. ej. `content.publish`), resueltos a un
  `Set` deduplicado por `findUserWithPermissions()` e inyectados en el JWT.
- **Enforcement**: preHandlers `fastify.authenticate` (verifica JWT) y
  `fastify.authorize(permission)` (comprueba permisos del payload).

## Consecuencias

**Positivas**

- Autorización por petición sin roundtrip a la BD (los permisos viajan en el JWT).
- El refresh token revocable + rotación mitiga el robo/replay; el hash en BD evita exponer
  el token en claro si la base se filtra.
- Los bloques pueden declarar permisos (`manifest.permissions`) que se registran en la
  tabla `Permission`.

**Negativas / costes**

- Los cambios de permisos no se aplican hasta que se emite un nuevo access token (el JWT
  es una instantánea); el frontend refresca permisos vía `GET /auth/me`.
- La revocación de access tokens no es inmediata (solo vía expiración de 15 min).

## Notas

- `JWT_REFRESH_SECRET` está definido en el entorno pero **no se usa** (el refresh token no
  es un JWT). Ver `docs/architecture/auth-rbac.md`.
- `@webs/core` declara además `manager` y `guest` en `SystemRole`, pero el seed solo crea
  cuatro roles.
