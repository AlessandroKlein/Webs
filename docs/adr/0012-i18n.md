# ADR-0012: Estrategia de internacionalización (ES/EN/PT)

- **Estado:** Aceptado
- **Fecha:** 2026 (refactorización global de Webs, Milestone 2)
- **Decisión:** Formalizar el soporte de **tres locales** — **español (es, default)**, **inglés (en,
  fallback)** y **portugués (pt)** — sobre el paquete `@webs/i18n` (`packages/i18n`) con
  **i18next + react-i18next**. Los locales base viven en `packages/i18n/src/locales/{es,en,pt}.ts`;
  el administrador puede **sobrescribir** cualquier cadena desde la UI (tabla `Translation`) y cada
  plugin aporta sus propias traducciones vía `plugin.json`. Un **selector de idioma** (`language
  switcher`) en el shell (admin y público) persiste la elección en `localStorage` (`webs-locale`).

## Contexto

La plataforma se vende en LATAM (español/portugués) y apunta a mercados angloparlantes. El código
actual **ya implementa la mayor parte** de esta estrategia:

- `packages/i18n/src/index.ts` define `DEFAULT_LOCALE = 'es'`,
  `AVAILABLE_LOCALES = [{es, Español}, {en, English}, {pt, Português}]`,
  `SUPPORTED_LOCALES = ['es', 'en', 'pt']`, `baseResources = { en, es, pt }`, y
  `createI18n(options)` → `i18next.createInstance` con `fallbackLng: 'en'`,
  `supportedLngs: [...SUPPORTED_LOCALES]`, `interpolation: { escapeValue: false }`.
- Los locales base son `packages/i18n/src/locales/{es,en,pt}.ts` (claves planas punteadas).
- `docs/architecture/i18n.md` documenta dos niveles: recursos base + sobrescritura por UI mediante
  la tabla Prisma `Translation` (`@@unique([locale, namespace, key])`), con endpoints
  `GET /locales` y `GET/PUT /translations` (permisos `translation.read`/`translation.write`).
- `apps/web/src/lib/i18n.ts` arma la instancia con `baseResources` y `setLocale` (persiste en
  `localStorage['webs-locale']`); el `AdminLayout` muestra un selector de idioma.

El ADR formaliza lo que ya existe y fija las reglas para no divergir.

## Decisión

1. **Tres locales oficiales, en este orden de prioridad:** `es` (default) → `en` (fallback) →
   `pt`. No se añaden locales sin pasar por este ADR (o una revisión de su costo de mantenimiento).
2. **`@webs/i18n` es la única fuente de verdad de los locales base.** Ningún paquete o app define
   catálogos `es`/`en`/`pt` por su cuenta; consumen `baseResources`/`createI18n`.
3. **Claves planas punteadas** (`nav.plugins`, `settings.general.title`) en los tres locales; una
   clave que falte en `es`/`pt` cae a `en`, y si falta en `en` se muestra la clave (para detectarla).
4. **Sobrescritura por UI** (tabla `Translation`) manda sobre los recursos base en runtime; el
   admin edita las cadenas por `locale + namespace + key`.
5. **Traducciones de plugins** en `plugin.json` → `manifest.translations` (locale → clave → texto),
   fusionadas por el loader/registro en runtime (`registerTranslations`).
6. **Language switcher** en el shell (admin y público): lista `AVAILABLE_LOCALES`, cambia
   `i18n.changeLanguage`, persiste en `localStorage['webs-locale']`, y ajusta `<html lang>`.

## Consecuencias

**Positivas:**

- Cobertura real de LATAM (es/pt) + mercados EN sin recompilar.
- El cliente final puede ajustar textos sin tocar código (tabla `Translation`).
- Los plugins se localizan solos (contrato `manifest.translations`), sin tocar `packages/i18n`.
- Un solo paquete evita catálogos duplicados entre `apps/web` y `apps/api`.

**Negativas:**

- Tres locales multiplican el esfuerzo de mantenimiento de cadenas (toda clave nueva debe tener
  `es`/`en`/`pt`).
- `docs/architecture/i18n.md` está parcialmente desactualizado (aún dice «es/en»); hay que
  sincronizarlo con este ADR.
- Discrepancias conocidas a resolver: (1) la fusión de traducciones del admin con el shell no está
  cableada del todo; (2) falta un plugin de ejemplo con `translations` que sirva de referencia.

## Notas

- Implementación de referencia: `packages/i18n/src/index.ts` y `packages/i18n/src/locales/*.ts`.
- Doc detallada: `docs/architecture/i18n.md`.
- Relación con ADR-0005: las traducciones de plugins se registran junto al menú nativo en el
  loader (`apps/api/src/plugins/loader.ts`).
