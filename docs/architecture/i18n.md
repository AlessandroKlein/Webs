# Internacionalización (i18n)

## Resumen

La internacionalización se apoya en **i18next** y **react-i18next**. Existen dos niveles:

1. **Recursos base** — traducciones compiladas en `@webs/i18n` para `es` y `en`.
2. **Sobrescritura desde la UI** — una tabla `translations` en la BD que el administrador
   edita para reemplazar o añadir claves.

## Locales base (`@webs/i18n`)

`packages/i18n/src/index.ts` exporta:

```ts
export const DEFAULT_LOCALE = 'es';
export const SUPPORTED_LOCALES = ['es', 'en'] as const;

export const baseResources = {
  en: { translation: en },
  es: { translation: es },
};

export function createI18n(options: CreateI18nOptions = {}): i18n
```

- `packages/i18n/src/locales/es.ts` y `en.ts` contienen claves **planas con notación de
  punto** (`app.name`, `common.save`, `nav.dashboard`, `auth.login`, `theme.label`, …).
- `createI18n()` devuelve una instancia de i18next preconfigurada (fallback `en`,
  `supportedLngs: ['es','en']`, `interpolation.escapeValue: false`) y acepta
  `options.resources` para **fusionar recursos adicionales en runtime** (por ejemplo,
  traducciones de bloques). El backend puede usar la misma instancia para correos y
  notificaciones.

## Frontend

`apps/web/src/lib/i18n.ts` inicializa la instancia global:

```ts
import { baseResources, DEFAULT_LOCALE } from '@webs/i18n';

void i18next.use(initReactI18next).init({
  lng: localStorage.getItem('webs-locale') ?? DEFAULT_LOCALE,
  fallbackLng: 'en',
  supportedLngs: ['es', 'en'],
  resources: baseResources,
  interpolation: { escapeValue: false },
});

export function setLocale(locale: string) {
  localStorage.setItem('webs-locale', locale);
  return i18next.changeLanguage(locale);
}
```

El selector de idioma del panel (`apps/web/src/layouts/AdminLayout.tsx`) llama a
`setLocale()` con `es`/`en`.

## Sobrescritura desde la UI (tabla `translations`)

El administrador puede sobrescribir o añadir traducciones sin tocar el código. Persisten
en la tabla `Translation` de Prisma:

```prisma
model Translation {
  id        String   @id @default(uuid())
  locale    String
  namespace String   @default("translation")
  key       String
  value     String
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  @@unique([locale, namespace, key])
}
```

API (`apps/api/src/modules/translations/routes.ts`):

```text
GET /api/v1/locales        → { locales: ['es','en'], defaultLocale: 'es' }   (público)
GET /api/v1/translations   → lista + mapa "namespace:key" → value           (translation.read)
PUT /api/v1/translations   → upsert por [locale, namespace, key]            (translation.write) + audit
```

El `PUT` recibe `{ locale, namespace = 'translation', key, value }` y hace `upsert` usando
la clave compuesta `locale_namespace_key`. La UI de lectura es
`apps/web/src/features/translations/TranslationsPage.tsx` (lista la tabla).

### Cómo se fusionan (intención de diseño)

El mecanismo previsto es: el frontend carga las traducciones del admin (`GET
/translations`) y las inyecta en i18next mediante `createI18n({ resources })` (o
`i18next.addResourceBundle`), de modo que **sobrescriben** los recursos base. El
`@webs/i18n` README lo describe así: «Las traducciones definidas por el administrador en
la UI se cargan en runtime y se fusionan sobre estos recursos base».

> Estado actual: la infraestructura está lista (tabla + endpoints + opción `resources` de
> `createI18n`), pero `apps/web/src/lib/i18n.ts` inicializa solo `baseResources` y no hay
> código en el shell web que, al arrancar, consulte `GET /translations` y las fusione. Ver
> discrepancias.

## Traducciones aportadas por bloques

Los bloques aportan sus propias cadenas por dos vías posibles:

1. **Recursos compilados** — un bloque puede exportar recursos i18next e inyectarlos vía
   `createI18n({ resources })` o `addResourceBundle`.
2. **Claves en la BD** — un bloque puede insertar/servir claves en la tabla `translations`
   (mismo mecanismo de sobrescritura que el admin).

El `ClientBlockContext` inyecta `i18n` al bloque (`t(key)`, `locale`), de modo que el
`mount` del cliente traduce con la instancia activa (ver `apps/web/src/blocks/BlockSlot.tsx`):

```ts
const i18n: BlockI18n = {
  locale: i18next.language,
  t: (key, options) => i18next.t(key, options),
};
```

## Discrepancias observadas

1. **La fusión de traducciones del admin no está cableada.** `createI18n` soporta
   `resources`, y el backend expone `/translations`, pero el shell web no las carga ni
   fusiona en runtime; solo se cargan los `baseResources`.
2. **No hay traducciones de bloque registradas de ejemplo.** El SDK define `BlockI18n`,
   pero el bloque de ejemplo no aporta ni consume claves traducidas (usa `config.greeting`
   directamente).
